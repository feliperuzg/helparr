# `site/` — the landing page

The page at <https://feliperuzg.github.io/helparr>. Hand-written HTML and CSS,
no build step, no framework, no dependencies. `index.html` is the whole page and
`styles.css` is the whole stylesheet.

It is not the application, and the application never serves it. `site/` is
excluded from the Docker build context and `scripts/verify-image.mjs` asserts
that the exclusion held.

## Preview it

```bash
npm run site        # assembles .site/
open .site/index.html
```

`npm run site` copies three trees into `.site/`: this directory, the generated
screenshots from `docs/screenshots/`, and `public/logo.svg` as the favicon. It
substitutes nothing and templates nothing — what you open is byte-for-byte what
GitHub Pages serves. `.site/` is build output and is gitignored.

Opening `site/index.html` directly also works, but the four screenshots and the
favicon will be missing: they only arrive at their published paths after the
copy. Use `.site/` when the images matter.

## What is checked, and where

Five specs cover the site. Three run in the fast `npm test` lane and two in the
browser lane behind `npm run test:a11y`:

| Spec | Claim |
|---|---|
| `test/site-facts.test.ts` | Every `[data-fact]` on the page equals what the repository says |
| `test/site-links.test.ts` | Every link and asset resolves inside the assembled tree |
| `test/site-weight.test.ts` | Transfer weight is within `site/weight-baseline.json` |
| `test/site-a11y.test.ts` | Zero WCAG 2.1 AA violations, at three viewports |
| `test/site-viewport.test.ts` | Readable with JS off, no sideways scroll at 360 px, every request first-party |

The deploy is the only part that is *not* a required check. A publish can fail
for reasons outside the repository, and a required check that goes red for
someone else's outage teaches people to merge past red. Correctness is gated;
publication is not.

## The two things that need a human

**On a release.** The version on the page is hand-written. Bumping
`package.json` to `0.2.0` makes `site-facts` fail until `<dd
data-fact="version">` in `index.html` says `v0.2.0` too. That failure is the
feature — a stale version on a landing page is exactly the drift this page's
checks exist to catch — but it does mean the release edits one more line.

**When the description changes.** `package.json`'s `description` is canonical:
the hero sentence is checked against it, and GitHub's About field is set from
it. Nothing in CI can see the About field, so after editing the description,
push it up:

```bash
gh repo edit -d "$(node -p "require('./package.json').description")"
```

## Adding to the page

Two rules, both enforced:

1. **A claim about the project gets a `data-fact` attribute** and a row in
   `FACTS` in `test/site-facts.test.ts` naming the file it was copied from. A
   claim with no source fails the "every data-fact has a source" assertion —
   that is deliberate, and the fix is to point it at a file, not to remove the
   attribute.
2. **An asset changes the weight budget.** `site-weight` compares the
   assembled tree against `site/weight-baseline.json` file by file, so a new
   file fails even if it fits under the total. If the addition is intended,
   update the baseline in the same commit and say why.

No images live in this directory. The screenshots are generated by
`npm run build:screenshots` and have exactly one home, `docs/screenshots/`,
which is also what the README embeds; `site-links` asserts the page shows those
files and not copies of them.

## The two deliberate deviations from `arx/design/DESIGN.md`

Both are marked `DEVIATION` inline in `styles.css` and were ratified as ADRs in
`arx/changes/static-landing-site/plan.md`. Do not "fix" them silently:

- **Fonts (ADR-7)** — JetBrains Mono is self-hosted as a 31 kB latin subset
  instead of loaded from Google Fonts, and IBM Plex Sans is dropped for a
  system sans stack. The contract's `<link>` would be a third-party request.
- **Accent (ADR-8)** — `--color-accent` carries the call to action here rather
  than status. Reverting it puts `--color-primary` on the buttons, which is
  2.38:1 against the background and fails WCAG 1.4.11.
